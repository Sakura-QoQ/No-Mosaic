# FallenFlower NoMosaic reverse engineering and permanent patch guide

Updated: 2026-09-26  
Final status: installed, structurally verified, and visually validated by the user  
Target: the current local build under `D:\FallenFlower`

## 1. Final conclusion

FallenFlower's private-area pixelation is not baked into a texture and is not
a full-screen post-process. It is generated by a dedicated Unity `GameObject`,
`SkinnedMeshRenderer`, and `Mosaic` material.

The successful solution does not depend on a runtime Mod. In
`FallenFlower_Data\sharedassets0.assets`, it preserves the original `Mosaic`
material name and PathID 83 while replacing the complete serialized material
payload with the game's transparent `Hided` material. References and integrity
checks therefore remain valid, but renderers using the material no longer
produce pixelation.

After installation, launch `FallenFlower.exe` normally. Neither
`--enable-mods` nor `UcModLauncher.exe` is required.

## 3. Entry-point discovery

The generated TypeScript SDK exposes this component:

```ts
declare class CheckMosaic extends UnityEngine.MonoBehaviour {
    gameObjects: UnityEngine.GameObject[];
    materials: UnityEngine.Material[];
}
```

This shows that the game maintains references to a set of censorship objects
and materials. The first hypothesis treated `CheckMosaic` as an enable/disable
control, but later disassembly of `GameAssembly.dll` proved that it is an
integrity monitor.

Key IL2CPP functions:

| Function | RVA | Behavior |
|---|---:|---|
| `CheckMosaic.Start` | `0x781100` | Calls `Shader.Find`; enters the error path if the expected Shader is missing |
| `CheckMosaic.Update` | `0x7811D0` | Iterates `materials` and `gameObjects` and checks material, Shader, and object references |
| `CheckMosaic.MosaicError` | `0x7810A0` | Calls `Application.Quit`, obtains the current process, and calls `Process.Kill` |

Consequently, the patch must not delete `CheckMosaic`, clear its arrays,
destroy referenced objects, or leave a material with a null Shader. This is why
the early approach that directly disabled monitored references was unreliable.

## 4. Unity resource implementation

AssetRipper 1.3.10 and AssetsTools.NET v8 established the following serialized
resource structure:

- Pixelation is produced by a dedicated `GameObject`.
- The object contains a dedicated `SkinnedMeshRenderer`.
- The renderer uses `Assets/Material/Mosaic.mat`.
- `Mosaic.mat` uses `Shader Graphs/NotMosaic`.
- Original material properties include `_Size = 120` and `_UIBlur = 2`.
- Eleven serialized objects named `Mosaic` exist across six monster prefabs and
  the Hotel/Street scenes.
- The live material in `sharedassets0.assets` is Material PathID 83.
- The original `Mosaic` Shader pointer is `0:691`.
- The built-in `Hided` material uses a transparent HDRP/Unlit configuration
  with Shader pointer `1:165`.

This evidence rules out both the baked-texture and full-screen post-process
hypotheses.

## 5. Attempted approaches and failure analysis

### 5.1 Disable referenced objects at runtime

The first Mod found `CheckMosaic` through the SDK and disabled objects in its
reference arrays. This misread their semantics: they are integrity-monitor
targets, not simple feature switches. The modification could trigger the exit
path and still miss the actual dynamic renderer instance.

### 5.2 Disable scene objects named Mosaic

A corrected version recursively searched for objects named `Mosaic`. It was
later changed to scan only during scene, NPC, and interaction lifecycle events,
removing `Update`/`LateUpdate` scans. This eliminated continuous traversal
overhead, but dynamic characters, pseudo-scene hierarchies, and instance timing
made coverage inconsistent.

### 5.3 Mark eleven serialized GameObjects inactive

All eleven objects in `resources.assets`, `level1`, and `level6` were written
with `m_IsActive=false`, and independent readback confirmed the change. The
running game still displayed pixelation, showing that the live instance or
material path was not controlled exclusively by those serialized active flags.

### 5.4 Modify `_Size`

Setting `_Size` to zero enlarged the sampling unit and produced larger pixel
blocks. The direction was opposite to the intended effect. A later value of
8192 attempted sub-pixel sampling, but runtime loading, material instances, and
launch conditions made the result inconsistent. This experiment established
that `_Size` controls the sampling grid; zero does not disable the effect.

### 5.5 Replace the material with Hided at runtime

NoMosaic v2.4.0 attempted to obtain the built-in `Hided` material from
`CheckMosaic.materials` and copy its Shader, properties, and render state to the
live `Mosaic` material. The design was sound, but it still depended on optional
Mod loading. Direct startup logged:

```text
[ModLoader] Optional mods are disabled. Pass --enable-mods to enable plan-based mod loading.
```

At least the final reported runtime-Mod failure was therefore not a v2.4.0
effect test: the log contained no NoMosaic version marker because the optional
Mod was not loaded.

## 6. Successful permanent patch

The final design moves the validated transparent-material replacement from
runtime code into the serialized resource.

Patch procedure:

1. Open `FallenFlower_Data\sharedassets0.assets` with AssetsTools.NET.
2. Enumerate `Material` assets and locate `Mosaic` and `Hided` by `m_Name`.
3. Read and record both `m_Shader` PPtrs.
4. Change the in-memory `Hided` `m_Name` to `Mosaic`.
5. Create a replacement from the complete serialized `Hided` field tree.
6. Write that payload at the original `Mosaic` PathID 83.
7. Preserve the PathID and name so existing references continue to resolve.
8. Reload the output and verify that `Mosaic` and `Hided` use the same Shader
   pointer.

Core implementation:

```text
work\tools\MosaicAssetPatch\Program.cs
```

Essential logic:

```csharp
hidden.Field["m_Name"].AsString = "Mosaic";
var replacer = new AssetsReplacerFromMemory(
    instance.file,
    mosaic.Info,
    hidden.Field
);
```

The patch copies the complete transparent-material state instead of changing
only the Shader pointer. This carries across the HDRP/Unlit properties,
transparent blending, and render-queue state and avoids a partial replacement
where the new Shader still renders under the old material configuration.

## 8. Startup and Mod-manager state

The final patch resides directly in Unity resource files:

- Launch `FallenFlower.exe` normally.
- `--enable-mods` is not required.
- `UcModLauncher.exe` is not required.
- The obsolete NoMosaic entry was removed from `Mods\modloadplan.json`.
- The log message "Optional mods are disabled" is expected and does not affect
  the permanent patch.

The old v2.4.0 runtime package was deleted. The current release is
`versions\NoMosaic-Permanent-v1.0.0.zip`. It runs a local patch tool against the
user's own resource file and does not participate in Mod loading.

## 9. Performance impact

The final solution registers no `Update`, `LateUpdate`, or periodic scan and
does not execute NoMosaic through Jint. It only changes serialized material
data, so its runtime cost is equivalent to loading a normal material. Recursive
traversal and repeated scans from early prototypes are not part of the final
execution path.

## 10. Compatibility, updates, and recovery

- The patch depends on the current resource structure and PathID. If a game
  update replaces the resource, rescan and regenerate the patch rather than
  copying the old file over the new build.
- The user explicitly requested that no backup be retained, and all original
  resource backups were deleted.
- To restore the original game, use the platform's Verify/Repair Files feature
  or reinstall the game.
- Verification or reinstallation overwrites the patch. Rebuild the patch for
  the restored version if it is still needed.
- Do not combine the retired runtime NoMosaic implementation with the permanent
  resource patch.

overwriting the live resource. No original-file backup is retained on this
